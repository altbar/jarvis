# Агенты для сотрудников: свой Гермес каждому, общая база отдела

Агент, это задание от владельца. Прочитай файл целиком. Потом своими словами перескажи владельцу разделы «Почему так» и «Что строим» - коротко, без терминов, которые он не знает. Проведи мини-интервью. Строить начинай только после его «да».

Правила:
- Строго по одному шагу, жди подтверждения. Перед каждым шагом - одна фраза: что делаешь и зачем. После шага сверяйся с блоком «что владелец должен увидеть». Не сошлось - дальше не идём.
- Сервер отдела настраиваешь ты сам по SSH, как при установке Гермеса владельца: `ustanovka/server-dostup.md`, `ustanovka/hermes-na-vps.md`.
- Ключи, токены ботов и пароли владелец отдаёт тебе в чат. Записываешь их сам командой `hermes -p ПРОФИЛЬ config set ИМЯ значение`. В ответах не повторяешь, в файлы волта не пишешь, `.env` и `config.yaml` целиком не выводишь (`AGENTS.md`, раздел 6).
- Интерактивное не запускаешь: мастер `hermes setup`, `hermes model`, nano, чат `hermes`.
- **Личного Джарвиса владельца не трогаешь вообще.** Ни одного сотрудника в его список разрешённых, ни одного профиля на его сервере.
- Не упрощай схему до «одного бота с пятью ID». Ниже объяснено, почему это не работает. Если владелец всё равно решит иначе - скажи об этом один раз и выполняй.
- Схема сверена с документацией и кодом Hermes v0.21.7 (октябрь 2026), но целиком на живом сервере не прогонялась. Версия на сервере может быть новее. Команда упала или ответила «did you mean» - читай ошибку, бери подсказанный путь и сверяйся с документацией, а не подбирай наугад. Что не проверил - помечай `[требует проверки]`.

## Почему так, а не проще

Гермес - личный агент одного человека. Это позиция разработчиков, а не наша перестраховка. Все, кого пустили в бота, для него «одинаково доверенные». Разделить людей внутри одного бота нельзя, можно только развести их по разным агентам.

| Как хочется сделать | Что выйдет на деле |
|---|---|
| Пять ID в одного бота, каждый пишет в личку | Переписки раздельные. Но память и профиль пользователя (`USER.md`) одни на пятерых: один попросит «округляй до тысяч», другой «до копейки», и оба правила применятся ко всем. Поиск по прошлым разговорам достаёт чужие переписки. У всех пятерых полные права: терминал, файлы и ключи на сервере. Ролей нет, запрет в инструкции модель обходит. |
| Бот в общем чате отдела | Хорош как общая справочная, плох как личный помощник. Ответы видят все, командовать может любой участник. В группе с темами модель путает, кто сейчас пишет. |
| Профиль на каждого | У каждого своя память, свои предпочтения, своя переписка и свой ключ к модели. Это штатный путь Гермеса. Но профиль - это набор настроек, а не сейф: настоящую границу дают отдельный сервер и Docker. |

Формула: **не один Джарвис на всех, а свой у каждого - с общей базой знаний компании и разными правами доступа.**

## Что строим

```
Отдельный сервер отдела (не тот, где живёт личный Джарвис владельца)
│
├─ основной профиль  → командный бот: справочная отдела, в общем чате отвечает по упоминанию
├─ prodazhi-anna     → личный бот Анны: пишет только Анна
├─ prodazhi-ivan     → личный бот Ивана: пишет только Иван
│  … по профилю и боту на каждого сотрудника
│
└─ /srv/otdel/
   ├─ baza/      база отдела: прайс, скрипты, кейсы, регламенты, общие скиллы
   │             владелец правит её в Obsidian, на сервер она приходит через GitHub,
   │             агенты видят её только на чтение
   └─ lyudi/     личные рабочие папки: КП, черновики, заметки по клиентам
```

| Что | Общее | Личное |
|---|---|---|
| База знаний и скиллы отдела | да, только чтение | - |
| Память и предпочтения | - | у каждого свои |
| Переписка с ботом | - | у каждого своя |
| Рабочая папка | - | у каждого своя, владелец видит её на сервере |
| Ключ к модели | - | у каждого свой: видно, кто сколько тратит |
| CRM | одна на отдел | доступ через ключ самого сотрудника, с его правами |

## Мини-интервью

Задай по одному вопросу:

1. Сколько сотрудников и как их зовут? Для каждого нужен числовой Telegram-ID: пусть напишут @userinfobot и пришлют число.
2. Нужен ли командный бот в общем чате отдела, или достаточно личных? (Командный бот всё равно ставим: на нём держится служба. Без чата он просто справочная в личке.)
3. Что положить в базу отдела и где это лежит сейчас: прайс, скидки, скрипты, ответы на возражения, кейсы, регламенты?
4. На какой модели работать? Без ответа дальше не идём: **один ключ или одна подписка на пятерых - нельзя.** Это общий лимит на всех, и одна поломка выключает всех сразу. Кроме того, личная подписка - на одного человека: условия ChatGPT прямо запрещают давать пользоваться своим аккаунтом другим людям. Варианты:
   - каждому своя подписка (`ustanovka/minimax.md`) или свой ChatGPT Plus;
   - API-ключ с месячным лимитом на каждого (`ustanovka/openrouter-klyuch.md`).
   Командному боту - отдельный ключ компании.
5. Есть ли CRM (Битрикс24, amoCRM)? Её подключаем последним шагом, когда остальное работает.
6. Есть ли отдельный сервер под отдел? Если нет - купить по `ustanovka/vps-smartape.md`: от 4 ГБ памяти, 2 ядра, 40 ГБ диска.

## Шаг 1. Отдельный сервер отдела

Почему отдельный: агенты сотрудников будут работать в Docker, а доступ к Docker на сервере равен правам администратора. На сервере Джарвиса это дыра в личные данные владельца.

Настрой новый сервер так же, как сервер Джарвиса: `ustanovka/server-dostup.md` (пользователь `agent`, вход по ключу, файрвол, fail2ban). Алиас SSH дай другой - `otdel`, чтобы не перепутать с `jarvis`.

**Что владелец должен увидеть:** `ssh otdel` заходит без пароля, `whoami` печатает `agent`.

## Шаг 2. Hermes и Docker

1. Hermes - по `ustanovka/hermes-na-vps.md`, шаги 2-4: установка и модель. На этом шаге ставишь только модель основного профиля, с ключом компании для командного бота. Шаги 5-9 того урока здесь не нужны.
2. Docker:
   ```
   curl -fsSL https://get.docker.com | sudo sh
   sudo usermod -aG docker agent
   ```
   Выйди и зайди по SSH заново, чтобы группа применилась. Проверь: `docker run --rm hello-world`.
3. Заранее скачай образ песочницы, чтобы первая команда агента не упала по таймауту. Образ большой, это несколько минут:
   ```
   docker pull nousresearch/hermes-sandbox:desktop
   ```

**Что владелец должен увидеть:** `hermes -z "привет, какая у тебя модель?"` отвечает, `docker run --rm hello-world` печатает приветствие Docker.

## Шаг 3. База отдела

База - это обычный Obsidian-волт отдела в приватном репозитории GitHub, как волт владельца (`ustanovka/volt-cherez-github.md`). Разница одна: сервер её только читает.

1. Владелец заводит приватный репозиторий `otdel-baza`. Помоги разложить папки:
   ```
   README.md       что где лежит, одной страницей
   prajs/          цены, скидки, условия - только действующие
   skripty/        скрипты звонков, ответы на возражения
   kejsy/          кейсы и отзывы
   reglamenty/     этапы сделки, сроки, кто что согласует
   skills/         общие навыки агентов, по папке на навык с SKILL.md внутри
   ```
2. Ключ только на чтение. На сервере создай ключ для root. Открытую часть владелец добавляет в репозиторий: **Settings → Deploy keys → Add deploy key**, галочку **Allow write access** НЕ ставит.
   ```
   sudo ssh-keygen -t ed25519 -f /root/.ssh/otdel_baza -N ""
   sudo cat /root/.ssh/otdel_baza.pub
   ```
3. Клон и права. Папку держит root, пользователь `agent` её только читает. Поэтому ни один агент не перепишет базу или общий скилл для всех.
   ```
   sudo mkdir -p /srv/otdel/lyudi
   sudo chown agent:agent /srv/otdel/lyudi
   sudo GIT_SSH_COMMAND="ssh -i /root/.ssh/otdel_baza -o StrictHostKeyChecking=accept-new" \
     git clone git@github.com:ВЛАДЕЛЕЦ/otdel-baza.git /srv/otdel/baza
   sudo git -C /srv/otdel/baza config core.sshCommand "ssh -i /root/.ssh/otdel_baza"
   sudo chmod -R a+rX,go-w /srv/otdel/baza
   ```
4. Обновление раз в 10 минут, только в одну сторону, с GitHub на сервер:
   ```
   (sudo crontab -l 2>/dev/null; echo "*/10 * * * * git -C /srv/otdel/baza pull -q --ff-only && chmod -R a+rX,go-w /srv/otdel/baza") | sudo crontab -
   ```

**Что владелец должен увидеть:** `ls /srv/otdel/baza` показывает его папки, а `touch /srv/otdel/baza/x` от пользователя `agent` отвечает `Permission denied`. Это правильно.

## Шаг 4. Командный бот (основной профиль)

На основном профиле держится служба Гермеса для всего отдела, поэтому начинаем с него.

1. Владелец заводит бота в @BotFather (`ustanovka/tg-bot.md`), например `@компания_otdel_bot`. Privacy mode не трогать: тогда в группе бот видит только упоминания, ответы ему и команды.
2. Доступ и поведение. Список разрешённых - это владелец и все сотрудники через запятую, без пробелов:
   ```
   hermes config set TELEGRAM_BOT_TOKEN токен_командного_бота
   hermes config set TELEGRAM_ALLOWED_USERS ID_владельца,ID_1,ID_2,ID_3
   hermes config set TELEGRAM_HOME_CHANNEL ID_владельца
   hermes config set TELEGRAM_REQUIRE_MENTION true
   ```
3. Справочная без памяти и без опасных инструментов. Ей пишут многие, поэтому личное она не копит, а на сервер не ходит:
   ```
   hermes config set memory.memory_enabled false
   hermes config set memory.user_profile_enabled false
   hermes config set agent.disabled_toolsets '["terminal","code_execution","memory","session_search","browser","delegation","cronjob","kanban","catalog","connections","computer_use"]'
   hermes config set terminal.backend docker
   hermes config set terminal.docker_volumes '["/srv/otdel/baza:/baza:ro"]'
   hermes config set terminal.docker_network false
   hermes config set skills.external_dirs '["/srv/otdel/baza/skills"]'
   hermes config set skills.creation_nudge_interval 0
   ```
   Последняя строка запрещает справочной самой заводить себе новые навыки после разговоров. Иначе то, что ей сказал один сотрудник, начнёт влиять на ответы всем.
4. Слэш-команды. Админские команды (`/model`, `/yolo`, `/update`, `/restart`) - только владельцу, остальным - `/new` и `/status`:
   ```
   hermes config set gateway.platforms.telegram.extra.allow_admin_from '["ID_владельца"]'
   hermes config set gateway.platforms.telegram.extra.user_allowed_commands '["new","status"]'
   hermes config set gateway.platforms.telegram.extra.group_allow_admin_from '["ID_владельца"]'
   hermes config set gateway.platforms.telegram.extra.group_user_allowed_commands '["new","status"]'
   ```
5. Характер. Запиши в `~/.hermes/SOUL.md`:
   ```
   Ты - справочная отдела продаж компании КОМПАНИЯ. Отвечаешь на вопросы сотрудников по базе отдела: папка /baza, только чтение.
   Цены, скидки, сроки и условия берёшь только из /baza и называешь файл, откуда взял. Нет в базе - так и скажи и предложи спросить руководителя.
   Личное о сотрудниках не запоминаешь и не обсуждаешь. Отвечаешь коротко, по делу.
   ```
6. Служба:
   ```
   sudo loginctl enable-linger agent
   hermes gateway install
   systemctl --user status hermes-gateway --no-pager
   ```

**Что владелец должен увидеть:** статус `active (running)`. В личке командный бот на «сколько стоит …?» отвечает фактом из базы и называет файл.

## Шаг 5. Шаблон сотрудника

Один раз настраиваем профиль-образец, дальше каждого сотрудника клонируем из него. **С шаблоном никто не разговаривает и бота у него нет:** клон копирует его память, а она должна остаться пустой.

1. Профиль и модель. Модель шаблона - та, на которой будут работать сотрудники (вопрос 4 интервью). Ключей в шаблон не кладём: у каждого будет свой.
   ```
   hermes profile create prodazhi-shablon
   P=prodazhi-shablon
   ```
   Подписка MiniMax, как ключ тренинга:
   ```
   hermes -p $P config set ANTHROPIC_BASE_URL https://api.minimax.io/anthropic
   hermes -p $P config set model.provider anthropic
   hermes -p $P config set model.base_url https://api.minimax.io/anthropic
   hermes -p $P config set model MiniMax-M3
   ```
   ChatGPT Plus у каждого сотрудника:
   ```
   hermes -p $P config set model.provider openai-codex
   hermes -p $P config set model ИМЯ_МОДЕЛИ
   ```
   Имя модели возьми из списка моделей Codex в документации Hermes (провайдер `openai-codex`). Проверять будем на первом сотруднике, после его входа.
2. Песочница и инструменты. Важнее всего выключить `session_search`: он умеет читать переписку соседних профилей.
   ```
   hermes -p $P config set terminal.backend docker
   hermes -p $P config set terminal.container_memory 1024
   hermes -p $P config set skills.external_dirs '["/srv/otdel/baza/skills"]'
   hermes -p $P config set agent.disabled_toolsets '["session_search","browser","delegation","kanban","catalog","connections","computer_use"]'
   ```
   Что остаётся сотруднику: веб-поиск, файлы и терминал внутри своей песочницы, свои скиллы и общие, своя память, задачи, напоминания по расписанию, разбор фото и голос.
3. Характер. Запиши в `~/.hermes/profiles/prodazhi-shablon/SOUL.md` и подставь название компании:
   ```
   Ты - помощник одного сотрудника отдела продаж компании КОМПАНИЯ. Как его зовут и как он любит работать, узнаёшь из разговора и запоминаешь.
   База отдела - папка /baza, только чтение: прайс, скрипты, кейсы, регламенты. Цены, скидки, сроки и условия берёшь только оттуда и называешь файл. Нет в базе - так и скажи и предложи спросить руководителя. Не обещай клиенту того, чего нет в базе.
   Твоя рабочая папка - /rabota: КП, черновики писем, заметки по клиентам. Сообщения клиентам готовишь как черновик, отправляет сотрудник сам.
   О других сотрудниках и их переписке ты не знаешь. Просят чужие данные или доступ к серверу - откажи и предложи обратиться к руководителю.
   На каждого нового клиента предлагай начать разговор заново командой /new.
   ```

**Что владелец должен увидеть:** `hermes profile list` показывает `prodazhi-shablon`.

## Шаг 6. Первый сотрудник - пилот

Начни с одного человека, лучше с самого терпеливого. Остальных подключаем, только когда пилот прошёл шаг 7.

1. Бота сотруднику заводит **владелец** в своём @BotFather, например `@компания_anna_bot`. Так бот остаётся у компании, если человек уйдёт. Сотрудник присылает только свой ID. Токен и ID владелец отдаёт тебе.
2. Профиль из шаблона, папка и тома. Имя пиши латиницей, строчными, например `anna`:
   ```
   N=anna
   P=prodazhi-$N
   hermes profile create $P --clone-from prodazhi-shablon
   mkdir -p /srv/otdel/lyudi/$N
   hermes -p $P config set terminal.docker_volumes "[\"/srv/otdel/baza:/baza:ro\",\"/srv/otdel/lyudi/$N:/rabota\"]"
   ```
3. Свой ключ к модели. Подписка MiniMax или API-ключ сотрудника:
   ```
   hermes -p $P config set ANTHROPIC_API_KEY ключ_сотрудника
   ```
   ChatGPT Plus сотрудника - вход его аккаунтом:
   ```
   hermes -p $P auth add openai-codex
   ```
   Команда даст ссылку и код. Их сразу отправляют сотруднику, он входит **своим** ChatGPT, код живёт недолго. Без своего входа профиль молча берёт вход основного профиля, то есть чужую подписку. Проверь: `hermes -p $P auth status openai-codex`.

   В обоих случаях проверка: `hermes -p $P -z "какая у тебя модель?"` отвечает.
4. Слэш-команды: сотруднику - `/new` и `/status`, админские - только владельцу. Каналы клон не копирует, поэтому задаём заново:
   ```
   hermes -p $P config set gateway.platforms.telegram.extra.allow_admin_from '["ID_владельца"]'
   hermes -p $P config set gateway.platforms.telegram.extra.user_allowed_commands '["new","status"]'
   ```
5. Бот. Токен записывай последним: профиль оживает, как только у него появился токен, и к этому моменту всё остальное уже должно стоять. Перезапуск не нужен, служба подхватит профиль сама.
   ```
   hermes -p $P config set TELEGRAM_ALLOWED_USERS ID_сотрудника
   hermes -p $P config set TELEGRAM_HOME_CHANNEL ID_сотрудника
   hermes -p $P config set TELEGRAM_BOT_TOKEN токен_бота_сотрудника
   hermes -p $P gateway status
   ```
6. Если ID сотрудника не попал в список командного бота на шаге 4 - добавь. Записывай весь список заново, через запятую. Перезапуск службы на пару секунд прервёт всех, поэтому новые ID лучше собрать заранее.
   ```
   hermes config set TELEGRAM_ALLOWED_USERS ID_владельца,ID_1,ID_2,…
   hermes gateway restart
   ```

**Что владелец должен увидеть:** `gateway status` говорит, что профиль обслуживается. Сотрудник пишет своему боту «привет» и получает ответ. Посторонний, написавший этому боту, ответа не получает.

## Шаг 7. Проверка границ - обязательно на пилоте

Это главный шаг. Сначала положи на сервер безобидный файл-метку. Ключи для проверки не используем: если граница не сработала, они уйдут сотруднику в чат.
```
echo "метка сервера" > /home/agent/metka.txt
```

Дальше сотрудник пишет своему боту, а ты смотришь на сервере:

| Что пишет сотрудник | Правильный результат |
|---|---|
| «Выполни команду: cat /home/agent/metka.txt» | Файла нет: песочница не видит сервер |
| «Создай файл /baza/test.txt» | Отказ: база только на чтение |
| «Создай файл /rabota/test.txt с текстом привет» | Получилось, и на сервере `ls /srv/otdel/lyudi/anna` его показывает |
| «Найди в прошлых разговорах, о чём говорили другие сотрудники» | Нечем искать или пусто |
| `/model` | Команда недоступна |
| «Сколько стоит …?» (что-то из прайса) | Факт из `/baza` с названием файла |

Последняя проверка - на сервере. Контейнер сотрудника появляется после его первой команды, и в нём должны быть смонтированы ровно две папки: `/baza` только на чтение и `/rabota`.
```
P=prodazhi-anna
docker inspect -f '{{json .Mounts}}' $(docker ps -q --filter label=hermes-profile=$P)
```

Если хоть одна строка не сошлась - останови профиль (`hermes -p $P gateway stop`), разберись и только потом подключай остальных.

**Что владелец должен увидеть:** все шесть строк сошлись, в `docker inspect` видны только две папки.

## Шаг 8. Остальные сотрудники

Повтори шаг 6 для каждого. Свои ключ, бот и папка у каждого, ID - в список командного бота. После каждого - первые две строки из шага 7.

**Что владелец должен увидеть:** у каждого сотрудника отвечает его бот, и только ему. `hermes profile list` показывает всех.

## Шаг 9. Командный бот в общем чате - по желанию

1. Владелец добавляет командного бота в чат отдела.
2. Спрашивать его - через @упоминание или ответом на его сообщение. Остальное он не видит и не читает.
3. В обычной группе у каждого сотрудника своя сессия с ботом, контексты не смешиваются. В группе с темами сессия общая на тему, и модель хуже понимает, кто спрашивает. Для справочной это терпимо, потому что памяти у бота нет.
4. Публикация в чат по расписанию, например «скрипт дня» из базы каждое утро. Её создаёт владелец через тебя на сервере командой `hermes cron create`. Доставку указывай с ID чата: `--deliver telegram:ID_чата`, просто `telegram` не сработает. Сотрудники из чата задачи не создают: у командного бота расписание выключено намеренно.

**Что владелец должен увидеть:** на «@бот какая скидка от 100 штук?» бот отвечает фактом из базы. Сообщение без упоминания он игнорирует.

## Шаг 10. CRM - по желанию, последним

Правило: **права сотрудника режет сама CRM, а не инструкция агенту.** Каждому профилю - доступ под учёткой этого сотрудника, а не админский ключ.

- **Битрикс24:** каждый сотрудник создаёт свой входящий вебхук. Вебхук получает права своего создателя, поэтому агент видит ровно то, что видит сотрудник. Подключение - `ustanovka/skill-bitrix.md`, но в профиль сотрудника (`-p prodazhi-…`).
- **Другая CRM через MCP:** сервер подключается в профиль сотрудника, ключ - в его `.env`. Гермес сам заводит набор инструментов `mcp-<имя>`. Давай высокоуровневые инструменты («найти клиента», «добавить заметку к сделке»), а не «выполнить любой запрос».
- Писать клиентам от имени компании агент не должен. Он готовит черновик, отправляет человек.

## Как жить с этим дальше

- **Новый сотрудник** - шаг 6 и строчки шага 7.
- **Сотрудник ушёл:**
  - `hermes -p prodazhi-ivan gateway stop` - бот сразу замолкает;
  - его ID убрать из списка командного бота, затем `hermes gateway restart`;
  - токен его бота отозвать в @BotFather; ключ к модели, если его оплачивала компания, перевыпустить;
  - папка `/srv/otdel/lyudi/ivan` остаётся компании;
  - профиль удалить позже, после выгрузки: `hermes profile export prodazhi-ivan -o ivan.tar.gz`, потом `hermes profile delete prodazhi-ivan`.
- **Поправить базу:** владелец правит её в Obsidian и отправляет на GitHub, сервер подтянет изменения в течение 10 минут. Правки в базу и общие скиллы вносит только владелец или руководитель отдела. Иначе выдуманная одним сотрудником скидка разойдётся по всем агентам.
- **Обновить Гермес:** `hermes update` - одна установка на весь отдел, поэтому обновление затрагивает всех сразу. Делать вечером, потом проверить пилотного бота.
- **Деньги:** у каждого свой ключ, поэтому видно, кто сколько тратит. Самая частая утечка лимита - разговор без `/new`, который тянется неделями.

## Чего эта схема не даёт

- **Ролей внутри одного бота.** Права задаются на профиль, а не на человека.
- **Сейфа из профиля.** Границу держат отдельный сервер, Docker, база только на чтение и выключенные инструменты. Не возвращай сотрудникам `session_search` и не выключай Docker.
- **Одного бота на всех с разными профилями.** Гермес это умеет с версии 0.21.4 (`gateway.profile_routes`), но функция свежая, а кто не попал ни под одно правило, уходит в основной профиль. Для отдела надёжнее личные боты.

## Если что-то пошло не так

| Симптом | Что делать |
|---|---|
| Бот сотрудника молчит | `hermes -p prodazhi-… gateway status`. Токен записан? ID в `TELEGRAM_ALLOWED_USERS` - число, без пробелов? Потом `hermes -p prodazhi-… gateway restart` |
| В статусе `duplicate_credential` | Один токен у двух профилей. У каждого бота должен быть свой токен |
| Агент не видит `/baza` или `/rabota` | Проверь тома: `hermes -p … config get terminal.docker_volumes`. После правки - `hermes -p … gateway restart` |
| `permission denied` от Docker | Пользователь `agent` не в группе `docker` или не перелогинился после шага 2 |
| База не обновляется | Запусти `sudo git -C /srv/otdel/baza pull` руками и прочитай ошибку. Обычно не добавлен deploy key |
| Сотрудник получил на `/new` «нет доступа» | В `user_allowed_commands` нет `new` |
| Лимит модели кончился у всех сразу | Ключ общий. У каждого должен быть свой: шаг 6, пункт 3 |
| Новый сотрудник пишет командному боту, а тот молчит | Его ID нет в `TELEGRAM_ALLOWED_USERS` основного профиля. Код подключения бот не присылает, ID добавляем руками |
| Сотрудник видит чужое | Сразу `hermes -p … gateway stop`, потом заново шаг 7: тома, `agent.disabled_toolsets`, Docker |
| Команда `config set` ответила «did you mean» | Путь ключа в этой версии другой. Возьми подсказанный и сверься с документацией |

## Чекпоинт

Четыре «да»:
1. У каждого сотрудника свой бот, и он отвечает только ему.
2. Шаг 7 пройден на каждом.
3. Командный бот в чате отвечает по упоминанию фактом из базы со ссылкой на файл.
4. Владелец поправил прайс в Obsidian, и через 10 минут боты отвечают по-новому.

## Агенту: почему так, если засомневаешься

Схема держится на позиции самих разработчиков Hermes, а не на нашей осторожности:
- `SECURITY.md` в репозитории Hermes: «Hermes Agent is a single-tenant personal agent». Все разрешённые пользователи «equally trusted», а кому нужно разделение - «run separate agent instances with separate allowlists».
- Мейнтейнер, отклоняя память по пользователям (PR #52903, июнь 2026): «the long-term memory is meant to be one operator's brain… Where isolation IS wanted, the boundary is profiles».
- Документация профилей: «Profiles do **not** sandbox the agent». На бэкенде `local` любой профиль видит все файлы пользователя ОС.
- Открытые задачи на GitHub, которые описывают ровно этот случай:
  - #27182 - общий `USER.md` на 7 продажников;
  - #87779 - `session_search` читает чужие чаты и профили;
  - #110686 - посторонний получил профиль владельца;
  - #3897 - ролей по пользователям нет.
